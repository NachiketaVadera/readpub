# ADR 0010: Structure-preserving preparation and a renderer location contract

Status: accepted and implemented.

A renderer computes locations in the browser DOM of prepared chapters, while
the core computes them from the original resource. The two agree only if
preparation keeps the element and character-data structure that CFIs count.
Removing a `script` element merges the text chunks around it and renumbers
later siblings, so a selection saved in the browser would resolve elsewhere.

Preparation therefore replaces active elements (`script`, `iframe`, `object`,
`embed`, `base`) with empty XHTML `template` placeholders that keep the ID,
removes only attributes from refresh `meta` elements and event handlers, and
appends reader styles after existing content. A document without a head gets
styles at the end of the root instead of a new first element. Legacy HTML
charset declarations are rewritten in place or appended. Tests assert that
every text offset has the same CFI in the original and prepared documents.

The contract for a renderer is: compute content-document CFIs relative to the
root element of the loaded chapter, counting elements and character data as
EPUB CFI specifies, and exchange them with the core together with the chapter
link. The core validates, corrects and converts them to locators; renderers
navigate with the corrected CFI or, lacking script access, with progression.
`readerLocationScript` is a reference implementation for browsers, verified in
a Chromium-based browser against CFIs generated by `DocumentText`. The session
never serves or runs it; hosts inject it with a platform API. Its Content
Security Policy still blocks publication scripts.

No preparation extension point is added: no concrete consumer requires one,
and every transformation must preserve the structure above.
